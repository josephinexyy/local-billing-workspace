# 产品案例：从业务文件到可操作的开票流程

## 问题与目标

小型服务业务需要维护客户资料、合同引用、付款通知、交易单据和收款凭证。信息重复填写，编号之间的关系也容易混淆。产品目标是让使用者以一笔业务为入口，找到当前状态和下一步操作。

主要使用者是单人经营者和独立服务提供者。当前范围是服务项目、HKD / USD 以及全额收款流程。

## 方案取舍

| 问题 | 考虑的方式 | 当前选择及原因 |
| --- | --- | --- |
| 操作入口 | 按单据分类；按业务聚合 | 按业务聚合，相关编号在查询时展开 |
| 数据保存 | 浏览器本地；服务端数据库 | 本地保存便于独立运行；接受手动备份和单人使用边界 |
| 公司资料 | 写入源码；浏览器配置 | 浏览器填写，降低复用时修改代码及意外公开资料的可能 |
| 客户识别 | 自动识别后直接保存；人工确认 | 显示识别结果后核对，避免将识别错误直接带入票面 |
| 恢复冲突 | 覆盖；跳过；阻止 | 相同记录跳过，不一致记录阻止整次合并 |
| 设置迁移 | 永远覆盖；永远不恢复；明确选择 | 导入前选择是否恢复，账本和设置一次保存 |
| 对外体验 | 要求先录入客户；虚构演示环境 | 独立演示账本，可以重置，减少初次体验成本 |

## 本次迭代及验证

公司设置原先需要单独保存。本次把完整工作区作为备份对象，同时兼容旧账本文件。导入前会显示记录数量及公司设置选项；恢复后核对编号、币种和业务状态。

公开仓库包含32项回归检查，覆盖重复导入、冲突、无效日期、公司设置校验、迁移及保存失败等场景。浏览器测试跑通了业务建立、收款、单张与成对 PDF，以及完整备份恢复。本地 OCR 使用一张清晰的虚构图片验证。

## 如何衡量效果

当前证据支持“流程可以完成、规则有明确行为”。尚未开展真实用户样本的耗时对照与长期使用研究。

下一轮应记录：

| 任务 | 记录方式 | 当前数据 |
| --- | --- | --- |
| 创建一笔业务并导出付款通知 | 相同输入条件下记录开始、完成和返工 | 待真实使用测量 |
| 再次为已有客户开单 | 记录重复输入字段和修改次数 | 待真实使用测量 |
| 从备份恢复到新环境 | 核对记录数、编号、币种、设置 | 虚构场景已通过 |
| 读取客户资料 | 按字段记录正确、需修正和无法识别 | 一张清晰虚构样例通过 |

仓库同时提供可复现的100条虚构记录备份恢复基准。它衡量内存中的代码路径，不用于推断人工操作节省时间。

## 后续范围

已加入签发方快照、模块拆分及浏览器回归。后续优先考虑部分收款和更多真实使用样本。团队协作、云端同步及银行接口需要另行定义权限、维护成本和数据可靠性目标。


## 历史单据与工程改进

发现的问题：票面曾读取当前公司设置，修改抬头或收款资料后，旧单据再次导出会随之变化。改为 PI 建立时保存签发方资料，后续 INV / RC 沿用；公司设置修改用于新业务。对旧记录明确标注可取得资料的来源，不声称恢复不存在的历史。

金额、编号和业务状态从页面抽出，备份、存储和票面分别维护；测试直接导入模块。新增浏览器检查实际执行开单、到账、下载、完整恢复、改公司设置和并发标签页操作。长内容 PDF 保持固定宽度并分页，避免整张过度缩小。

这些检查支持产品规则和技术行为的验证，尚不能代替真实用户效率研究。
